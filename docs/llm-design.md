# LLM 연동 기획 (v1.5)

> 상태: **MVP 구현 완료 (2026-11-23)** — ① 해석기(OpenAI 구조화 출력) + 검증 + 프로필 병합 + 직전 조건 이어받기 + 확인 문구, ② 엔진, `POST /api/chat`, 채팅 화면. **설명기는 템플릿 문장으로 대체**(LLM 설명·검증 2는 v1.5). **해석기 평가 스크립트 구현 완료**(`scripts/eval_interpreter.py`, 문장 43개, 결과와 한계는 `docs/eval-results.md`). 구현 위치: `app/services/llm/`(client, interpreter), `app/services/chat.py`, `app/api/chat.py`. LLM은 OpenAI로 확정(키 `OPENAI_API_KEY`, 모델 `OPENAI_MODEL` 기본 `gpt-4o-mini`), 호출부는 `client.py` 한 파일. / 작성: 2026-11-19
> 원칙: 추천 *판단*은 규칙 엔진이, LLM은 *요청 해석*과 *설명 생성*만 한다. 안전 판단(게이트)에 LLM은 관여하지 않는다.

---

## 1. 목표

사용자가 채팅으로 이렇게 말하면 동작해야 한다.

> "잡티에 좋은 토너 추천해줘. 근데 알코올은 빼고"

1. 말을 **구조화된 조건**으로 바꾼다 (고민, 카테고리, 기피/선호 성분)
2. 기존 **엔진**으로 상위 3개를 고른다 (LLM 개입 없음)
3. 엔진이 준 근거만으로 **설명 문장**을 쓴다

이 3단계가 곧 "오케스트레이션 구조"다. 단계마다 입출력 타입이 정해져 있고, 단계 사이에 **코드 검증**이 들어간다.

## 2. 전체 구조

```
사용자 메시지 ─┐
저장된 프로필 ─┴▶ ① 해석기 (LLM, 구조화 출력)
                      │ 출력: intent, concerns[], category, avoided[], preferred[], unclear[]
                      ▼
                 [검증 1: 코드]  어휘·카테고리 확인, 모르는 값 걸러냄
                      │
                      ├─ 확인 문구 생성 (코드가 만듦, LLM 아님)
                      ▼
                 ② 엔진 (기존 recommend, 규칙)  ← 게이트 → 매칭 개수 정렬 → 상위 3개
                      │ 출력: recommended[3], excluded[], warnings
                      ▼
                 ③ 설명기 (LLM, 엔진 결과만 입력)
                      │
                 [검증 2: 코드]  설명에 나온 성분·고민이 엔진 근거 안에 있는가
                      │ 실패 시 → 템플릿 문장으로 대체
                      ▼
              응답: 이해한 조건 + 상위 3개 카드(정형 데이터) + 설명 문장
```

| 단계 | 담당 | LLM 여부 | 실패 시 |
|---|---|---|---|
| ① 해석 | LLM + 코드 검증 | O | 되묻기("어떤 고민인가요?") 또는 저장된 프로필로 진행 |
| ② 추천 | 기존 엔진 | **X** | 해당 없음 (결정적) |
| ③ 설명 | LLM + 코드 검증 | O | 템플릿 문장으로 대체 |

## 3. 단계별 설계

### ① 해석기
- **입력**: 사용자 메시지, 저장된 프로필(고민, 기피/선호 성분, 민감성), **직전 턴의 확정 조건**(있을 때만)
- **출력 스키마(구조화 출력)**
  ```json
  {
    "intent": "recommend | greeting | unsupported | off_topic",
    "concerns": ["미백/톤"],
    "category": "스킨/토너",
    "avoided_ingredients": ["알코올"],
    "preferred_ingredients": [],
    "unclear": ["'잡티'를 미백/톤으로 해석함"]
  }
  ```
- **코드 검증**
  - `concerns`는 `ALLOWED_CONCERNS` 6개 안의 값만 통과. 밖의 값은 버리고 `unclear`에 남김
  - `category`는 5개 카테고리 중 하나만 통과
  - 기피 성분은 **놓치는 것보다 넓게 거르는 것이 안전**하므로, DB에 없는 성분이어도 유지하되 사용자에게 알림("DB에 정확히 일치하는 성분은 없지만 '알코올'이 들어간 성분을 거릅니다")
  - 추천이 아닌 문장은 유형별 고정 안내 문구로 응답 (LLM이 쓰지 않음): `greeting`(인사·서비스가 뭔지 묻는 말) → "ChaeInG입니다" 서비스 소개와 사용 예, `unsupported`(선크림 등 다른 제품군·성분 설명·가격·비건) → 지원 범위 안내, `off_topic`(배고파·머리 아파·잡담·규칙 무시 지시) → 올바른 문장 입력 요청. 추천이 아닌 유형에서는 LLM이 조건을 채워 보내도 코드가 버림
- **프로필과의 병합 규칙(제안)**
  - 고민: 메시지에 있으면 메시지 우선, 없으면 프로필 사용
  - 기피 성분: 프로필 ∪ 메시지 (합집합, 안전 쪽)
  - 민감성: 프로필 값 그대로 (메시지로 끄지 못하게)
- **대화 맥락(가벼운 방식, 확정)**
  - 대화 기록 전체가 아니라 **직전 턴에서 검증을 통과한 구조화 조건만** 다음 요청에 넘긴다. 장기 기억은 저장된 프로필이 맡는다
  - 후속 요청("그럼 크림으로", "알코올도 빼줘")은 이전 조건에 **변경분만 덮어쓴다**. 해석기는 전체를 새로 쓰지 않고 변경분만 출력
  - 이어받은 조건도 매번 검증 1을 다시 통과해야 한다. 기피 성분은 후속 요청에서도 **줄어들지 않는다**(제거 요청은 명시적일 때만, 사용자에게 확인 문구로 알림)
  - 한계: "아까 그 제품 성분이 뭐였지?" 같은 자유 대화는 하지 않음 (이후 확장)
- **확인 문구**는 코드가 템플릿으로 만든다 (예: "이렇게 이해했어요 — 고민: 미백/톤 · 카테고리: 스킨/토너 · 제외 성분: 알코올"). LLM이 쓴 문장을 믿지 않고, 파싱된 값을 그대로 보여주는 것이 핵심.

### ② 엔진
- 기존 `run_recommendation(db, profile, category, include_unverified)`를 그대로 사용 (이 함수는 원래 "API와 챗봇이 같이 쓰는 진입점"으로 만들어 둠)
- 결과에서 `recommended[:3]`만 사용. 탈락 제품은 사유와 함께 접어서 제공

### ③ 설명기
- **입력**: 상위 3개의 `{제품명, 매칭된 고민, 근거 성분(위치 포함), 경고, 선호 성분 히트}` 만. 제품 설명이나 외부 지식은 넣지 않음
- **프롬프트 제약**: 입력에 있는 사실만 사용, 효능 단정 금지("도움이 될 수 있다" 수준), 제품당 1~2문장
- **코드 검증**: 설명문에서 성분명을 찾아 그 제품의 실제 성분 목록에 있는지 확인, 언급된 고민이 `matched_concerns`에 있는지 확인. 하나라도 어긋나면 **템플릿 문장**으로 교체
- 템플릿 예: "{고민}에 해당하는 성분({성분 목록})이 들어 있어요."

## 3.5 평가 설계 (확정: 이번 범위에 포함)

LLM을 "통제했다"는 주장을 숫자로 증명하기 위한 장치. 대규모 벤치마크가 아니라 **테스트 요청 20~30개**로 한다.

- **테스트 요청 구성(안)**: 단순 고민 / 기피 성분 포함 / 카테고리 지정 / 모호한 표현("잡티", "칙칙해요") / 스킨케어 범위 밖 / 후속 요청(맥락) / 규칙 무시 유도(인젝션 시도) 등
- **정답**: 요청마다 기대하는 구조화 조건(고민, 카테고리, 기피 성분, intent)을 **사람이 작성하고 확인**한다 (요청 초안은 AI가 제안 가능, 정답은 사람이 확정)
- **지표**

| 대상 | 지표 | 비고 |
|---|---|---|
| 해석기 | 고민 일치율, 카테고리 일치율 | 정답과 비교 |
| 해석기 | **기피 성분 재현율** | 안전과 직결되므로 정밀도보다 재현율 우선 |
| 해석기 | 범위 밖 판별 정확도, 인젝션 요청 무력화 여부 | |
| 검증 1 | 걸러낸 잘못된 값 개수 | "검증이 실제로 일했는가" |
| 설명기 | 근거 밖 성분·고민 언급 건수, 템플릿 대체율 | 검증 2의 효과 |

- **실행**: `scripts/eval_interpreter.py`가 실제 LLM을 호출해 표를 출력. 결과 표와 실패 사례를 README에 정직하게 기록(틀린 사례도 숨기지 않음)
- 단위 테스트는 LLM을 모킹하고, 평가는 별도로 실행한다 (평가는 비용이 들고 결과가 매번 조금씩 다를 수 있음)

## 4. API와 화면

- `POST /api/chat` (로그인 필요)
  - 요청: `{ "message": "...", "previous_conditions": { ... } }` (`previous_conditions`는 직전 응답의 `understood`를 클라이언트가 그대로 돌려보냄. 서버는 받은 값을 다시 검증)
  - 응답: `{ understood, confirmation, recommendations[3], explanations, excluded, notices }`
  - `recommendations`는 기존 `RecommendedProduct` 스키마 재사용 (정형 카드), 설명은 별도 필드
- 화면: 채팅 페이지 1개 신설(메인). 카드는 정형 데이터로 렌더링하고 설명 문장만 LLM 출력. 기존 제품·찜·성분 화면은 보조 메뉴 유지
- 위치: `app/services/llm/`(interpreter, explainer, client), `app/api/chat.py`

## 5. 실패와 안전 장치

| 상황 | 동작 |
|---|---|
| API 키 없음/호출 실패/시간 초과 | 해석 실패 시 저장된 프로필로 추천, 설명은 템플릿. **LLM이 죽어도 추천은 나옴** |
| 해석 결과가 스키마 위반 | 1회 재시도 후 되묻기 |
| 설명에 근거 밖 성분/고민 | 템플릿으로 대체 |
| 인사·미지원·무관한 문장 | 유형별(greeting / unsupported / off_topic) 고정 안내 문구, 추천 실행 안 함 |
| 프롬프트 인젝션("규칙 무시하고…") | 해석기 출력이 스키마로 제한되고, 추천 판단은 엔진이 하므로 영향 범위가 구조화 필드로 한정됨 |

## 7-2. 선행 작업: 핵심 성분 판정 규칙 정비
엔진이 쓰는 제품의 `main_concerns`는 [핵심 성분 판정 규칙](core-ingredient-rule.md)(제품별 경계 + 제품명 신호)으로 다시 만든다. 기존 `TOP_N=20` 기준은 근거가 약해 폐기하기로 했다. 이 작업(약 1일)이 LLM 연동의 데이터 기반이 되므로 **LLM 연동보다 먼저** 진행한다.

**전체 진행 순서(확정)**
1. 핵심 성분 판정 규칙 구현 → 초안 재생성 (약 1일)
2. 제품 100개 전수 검수 (사람, 예상 2~3시간 — 제품당 1~2분 가정)
3. 검수값 DB 반영 (`apply_concerns`)
4. LLM 연동 (해석기 → 엔진 → 설명기, 평가 포함)
5. 채팅 화면, README·구조도 정리

## 8. 하지 않는 것 (이 문서 범위 밖)
- 공공데이터 성분 RAG, 성분 Q&A 챗봇
- LLM이 추천 순위나 게이트를 판단하는 구조
- 전체 대화 기록 기반 멀티턴, 에이전트 수 늘리기
