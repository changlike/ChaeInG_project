### 개발 방식
AI 에이전트와 협업한다. 설계를 먼저 함께 확정한 뒤, 코드는 AI가 초안을 작성하고 사용자가 리뷰하며 이해하는 방식으로 진행한다.

> 원칙: **"내가 모르는 구현이 하나도 없어야 한다"**

### 추천 챗봇 설계

별도의 "추천 폼" 페이지 없이 **챗봇 하나로 통합된 인터페이스**로 설계한다.

1. 사용자가 대화로 조건을 말한다.
2. 5장의 **스코어링 엔진**을 호출한다.
3. 챗봇이 그 결과를 자연어로 설명해서 답한다.

**LLM은 추천을 직접 판단하지 않는다.** 판단은 항상 Rule-Based 스코어링 로직이 하고, 챗봇은 그 결과를 설명하는 역할만 한다. 근거 있는 추천이라는 핵심 가치를 지키기 위함이다.

챗봇은 두 갈래로 나뉜다.

| 갈래 | 처리 방식 |
|---|---|
| ① 성분 Q&A | FAISS 검색 기반 RAG |
| ② 추천 요청 | 스코어링 엔진 호출 → 결과 설명 |
| 그 외 질문 | 고정된 안내 문구로 응답 |

자세한 라우팅/멀티턴 설계는 별도로 문서화할 예정이다.

## 4. 피부 프로필 항목

| 항목 | 값 | 비고 |
|---|---|---|
| 피부 타입 | 건성 / 지성 / 복합성 / 수부지 / 중성 (택1) | |
| 민감성 여부 | 체크박스 (`is_sensitive`) | 피부 타입과 **별도 축**. 민감성을 피부 타입의 한 종류로 넣지 않음 (건성이면서 민감성인 경우 등을 표현하기 위함) |
| 피부 고민 | 여드름/트러블, 모공, 홍조, 건조/보습, 미백/톤, 주름/탄력 (다중 선택) | 제품의 "주력 고민" 태그와 **동일한 어휘**를 공유 |
| 선호 성분 / 기피 성분 | 자유 텍스트 입력 | 성분 종류가 너무 많아 고정 목록으로 만들지 않음 |

6개 "피부 고민" 값은 제품 쪽 "주력 고민" 태그(`main_concerns`)와 같은 어휘를 쓴다. 사용자가 고른 고민과 제품에 태깅된 고민이 정확히 매칭되게 하기 위함이다.

## 5. 추천 방식 (스코어링 로직)

Rule-Based 스코어링 시스템이다. 단순 점수 합산이 아니라 **게이트(통과/탈락) + 가산점을 분리한 구조**로 설계한다.

- 이유: "피부 타입이 안 맞는데 다른 점수가 높아서 추천되는" 것 같은 논리적 모순을 막기 위함
- 안전/적합성 관련 항목은 감산이 아니라 **하드 게이트**로 처리

### 1단계: 게이트 (통과/탈락만, 점수 없음)

| 항목 | 판정 기준 |
|---|---|
| 민감성 유발 성분 | 민감성을 체크한 사용자 + 자극 유발 성분이 포함된 제품 → 탈락 |
| 기피/금지 성분 | 공공데이터 `REGULATE_TYPE = "금지"` 기준 금지 성분 포함 → 탈락 |
| 피부 타입 | **v1에서는 미적용** |

피부 타입 게이트를 뺀 이유: 실제 수집한 제품 데이터의 `skin_type_target`이 마케팅상 거의 전부 "모든 피부"로 되어 있어서(브랜드가 타깃을 넓히려는 목적) 게이트로 쓸 만큼 변별력이 없다고 판단했다. 나중에 성분 기반 추론 등 더 나은 신호가 생기면 추가한다. 사용자 프로필의 피부 타입 자체는 계속 수집한다.

게이트에서 탈락하면 최종 점수를 0으로 처리한다 (임시 기본값. 추후 "비추천 섹션 + 경고 표시"로 개선 가능).

### 2단계: 가산점 (게이트 통과 제품끼리만, 고민 매칭)

- 사용자가 고른 "피부 고민"과 제품에 태깅된 "주력 고민"이 **몇 개 겹치는지 개수를 그대로 표시**한다. (예: "고민 3개 중 2개 매칭")
- 100점 만점으로 환산하지 않고, 매칭 개수가 많은 순으로 정렬한다.
- 데이터 방식: 제품마다 "주력 고민"을 **수동 태깅**한다. 제품 CSV의 `main_concerns` 컬럼에 6개 값 중 해당하는 것을 사람이 직접 보고 입력한다.
- 나중에 성분표 자동 분석 방식으로 바꿀 수 있도록 **함수 인터페이스는 동일하게 유지**한다.

### 3단계: 경고 문구 (점수와 무관, 참고용 표시만)

- `REGULATE_TYPE = "한도"`(배합 한도가 있는 성분)가 포함된 경우 "배합 한도가 있는 성분이에요" 같은 경고만 표시한다.
- 게이트가 아닌 이유: 제품 데이터에 실제 함량(%) 정보가 없어서 한도 초과 여부 자체를 판정할 수 없기 때문이다.

## 6. 데이터 소스

| 데이터 | 출처 | 비고 |
|---|---|---|
| 기피/금지 성분 | data.go.kr "식품의약품안전처_화장품 사용제한 원료정보" API | 개발계정 자동승인, 하루 10,000건 무료. 필드: `REGULATE_TYPE`(금지/한도 등), `INGR_STD_NAME`, `CAS_NO`, `COUNTRY_NAME`, `LIMIT_COND`. 순서 정보·효능 정보는 없음 (순수 규제 데이터) |
| 제품/성분 | 올리브영에서 **수동 수집** | 자동 크롤링은 이용약관상 하지 않기로 결정. 사람이 직접 페이지를 보고 CSV에 옮겨 적는 방식. 카테고리별 CSV로 관리 (`data/` 폴더) |
| 고민-성분 매핑용 효능 데이터 | **미확보** | 없어도 2단계는 "제품 단위 수동 태깅"으로 우회 중 |

제품 데이터 현황 (2026-09-22 기준): 에센스/세럼/앰플 카테고리 17개 제품만 확보. 토너/로션/크림/선크림/클렌저는 아직 미수집.
