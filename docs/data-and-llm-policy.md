# 데이터 소스 조사 & LLM 데이터 채움 원칙

> 작성: 2026-10-15. 웹 조사는 검색 결과 기준이며 **"확인됨 / 미확인"을 구분**해서 적었다. 미확인 항목은 직접 확인 후 확정한다.

## 1. 성분 효능/주의사항(`efficacy`, `caution`) 데이터 소스 조사

| 후보 | 내용 | 확인 결과 | 쓸 수 있나 |
|---|---|---|---|
| 식약처 사용제한 원료정보 (data.go.kr API) | 금지/한도 성분 규제 정보 | 이미 사용 예정. **효능 정보 없음** (순수 규제 데이터) | 게이트·경고용 ✔ / 효능용 ✘ |
| data.go.kr 내 "화장품 성분 효능" 데이터 | 식약처 등이 제공하는 성분 효능 API가 있는지 | 이번 검색에서 **찾지 못함** (미확인). data.go.kr에서 "화장품", "원료" 키워드로 직접 검색 필요 | 미확인 |
| 대한화장품협회 성분사전 (KCID / kcia.or.kr) | 성분명 표준화·사전. INCI 기반 한글 표준명 | 열람용 사이트. **일괄 다운로드/API는 확인되지 않음** | 성분명 표준화 참고용 |
| 화장품 안전기준 등에 관한 규정 (식약처 고시, 법제처) | 별표1 사용금지 원료, 별표2 사용제한 원료 | 협회 FAQ에서 원료 사용 가능 여부 1차 확인처로 안내. 고시 원문은 법제처에서 열람 | 금지/한도 교차검증용 ✔ |
| EU CosIng (유럽연합 화장품 성분 DB) | INCI명, 기능(function), 규제 현황 | 공개 DB. **공식 일괄 다운로드 여부는 미확인**, 이용 조건 확인 필요 | 성분 기능(예: 보습제, 계면활성제) 분류 후보 |
| EWG Skin Deep | 성분별 위해 점수 1~10 | 공개 열람 가능. **공식 데이터 다운로드는 확인되지 않음**, 약관상 수집 제한 가능성 → 수집 금지 전제 | 참고용(수동 열람)만 |
| 민간 앱(화해, 코스지니 등) | 성분 등급·기능성 | 공식 API 없음 | 사용하지 않음 |

### 결론
- 공공 API 한 번 대조로 효능/주의사항이 채워지는 소스는 **현재까지 찾지 못함**.
- 현실적인 경로:
  1. **주의사항 중 규제성 내용**(금지/한도)은 식약처 데이터로 채움 → `caution`의 일부
  2. **효능**은 소수 핵심 성분(제품 데이터에 자주 등장하는 상위 N개)부터 **공신력 있는 출처를 사람이 확인하며 수기 정리**
  3. 나머지는 LLM 초안 + 검수 원칙(아래 2번)을 적용. 검수 전에는 화면에 "정리 중" 처리

### 추가로 유의미한 데이터 원천 (서비스 관점)
| 용도 | 후보 | 비고 |
|---|---|---|
| 성분명 정규화 | KCID(성분사전) 표준명, INCI명 | 제품마다 표기가 달라 매칭이 깨지는 문제 방지 (예: 하이알루로닉애씨드 ↔ 히알루론산) |
| 자극 유발 성분 목록(민감성 게이트) | 사전적 자극 성분(알코올, 향료, 에센셜 오일 등) 목록 + 식약처 **알레르기 유발 향료 25종 표시 의무 성분** | 알레르기 유발 성분 표시 규정은 식약처 고시 근거. 원문 확인 후 목록화 (미확인) |
| 기능성 화장품 성분 | 식약처 기능성화장품 심사 고시의 **미백·주름개선 고시 성분 목록** | 미백/톤·주름/탄력 고민과 성분을 연결하는 **공식 근거**로 사용 가능 → `main_concerns` 태깅의 근거 자료 |
| 성분 함량 | 제품 표기 ppm/% (CSV에 일부 존재, 예: 히알루로닉애씨드 1,000ppm) | `full_ingredients` 파싱 시 함량 표기 보존 |

> "미백/톤, 주름/탄력"은 식약처 **기능성화장품 고시 성분**이 공식 근거가 되므로, 6개 고민 중 이 둘은 LLM 없이 규칙 기반 태깅이 가능할 수 있음 (확인 필요).

## 2. LLM으로 데이터를 채울 때의 원칙 (초안)

핵심 가치("판단 근거를 항상 설명할 수 있어야 한다")를 지키기 위한 원칙. LLM은 **초안을 만드는 도구**이지 **판정자가 아니다**.

| # | 원칙 | 구체화 |
|---|---|---|
| 1 | **LLM 산출물은 항상 "초안" 상태로 저장** | `llm_draft`와 `verified`를 구분. 검수(`확인`) 전 데이터는 추천 엔진에서 사용하지 않음 |
| 2 | **출력 어휘를 닫는다** | `main_concerns`는 6개 고정 값 중에서만 선택. 목록 밖 값은 자동 폐기 |
| 3 | **근거를 함께 저장** | 태깅 결과와 함께 "어떤 성분 때문에 그렇게 판단했는지"를 저장. 근거가 없으면 채택하지 않음 |
| 4 | **입력은 제품 데이터에 한정** | 프롬프트에 성분표(`full_ingredients`)만 제공. 외부 지식으로 지어내지 않도록 "표에 없는 성분은 언급 금지" 명시 |
| 5 | **의학적 단정 금지** | 효능 문구는 "~에 도움을 줄 수 있음" 수준. 치료·완화·개선 단정 표현 금지 (화장품법상 표현 제한 고려) |
| 6 | **일회성 오프라인 작업** | 런타임에 LLM이 데이터를 채우지 않음. 배치로 생성 → CSV에 반영 → 사람이 검수 → DB 적재 |
| 7 | **사람 검수는 샘플이 아니라 전수 or 규칙 기반 점검** | 최소한 고위험(민감성·기피 관련) 항목은 전수 확인. 나머지는 일관성 검사(같은 성분 → 같은 판단)로 이상치 탐지 |
| 8 | **재현 가능하게 기록** | 모델명, 프롬프트 버전, 생성일을 함께 기록 |
| 9 | **효능/주의사항 텍스트는 출처 구분** | `source`: `규제데이터` / `수기` / `LLM초안`. 화면에 LLM초안은 별도 표기 |
| 10 | **안전 관련 판단은 LLM에 맡기지 않음** | 민감성 게이트·금지 성분은 공공 규제 데이터와 사람이 만든 목록만 사용 |

### 적용 예 — `main_concerns`
```
입력 : 제품명 + 성분표
출력 : {"concerns": ["건조/보습"], "evidence": {"건조/보습": ["글리세린", "소듐하이알루로네이트"]}}
검증 : concerns ⊂ 6개 고정 값, evidence의 성분이 실제 성분표에 존재하는지 자동 확인
저장 : CSV main_concern(초안) → 사람이 확인 → 확인 표시된 것만 DB 적재
```

### 3단계 결정 (2026-10-16): 제품별 LLM 태깅 대신 "성분→고민 사전 + 규칙" 방식

| 항목 | 내용 |
|---|---|
| 방식 | 사람이 검수하는 작은 사전(`data/ingredient_concern_map.csv`)과 규칙(`backend/app/services/concern_tagger.py`)으로 제품 고민을 판정. 같은 입력이면 항상 같은 결과 |
| LLM의 역할 | 사전 **초안 작성**까지만. 사전의 각 행은 사람이 검수 (현재 전부 초안) |
| 위치 규칙 | `top_n`: 앞쪽 `TOP_N`(=20)번째 안에 있을 때만 인정 / `any`: 소량으로도 쓰는 유효 성분이라 위치 무관 |
| 근거 데이터 | 보존제·증점제 첫 등장 위치 중앙값 18 (99개 제품 기준) → 20으로 설정, 조정 가능 |
| 후보 조건 | strong 성분 1개 이상, 또는 weak 성분 서로 다른 2개 이상 |
| 주력 고민 선택 | 후보 점수(strong 2점 + weak 1점) 높은 순으로 **제품당 최대 2개**. 동점이면 근거 성분이 앞쪽에 있는 고민 우선 |
| 저장 | 판정 결과는 검수용 CSV(`data/main_concerns_draft.csv`)로 출력. DB 반영은 사람이 확정한 값만, `is_concerns_verified=True`로 |
| 알려진 한계 | 상위 2개 제한 후에도 건조/보습이 99개 중 83개(1순위 68개)로 지배적. 히알루론산 변형 10종이 각각 strong으로 점수가 부풀려지기 때문(건조/보습 점수 중앙값 6 vs 그 외 고민 최고점 중앙값 3). 모공 사전이 빈약해 1개뿐 |
