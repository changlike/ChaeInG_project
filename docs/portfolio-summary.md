# ChaeInG 포트폴리오 정리 (초안)

> 이력서·포트폴리오에 옮길 내용만 모은 문서. LLM 연동은 아직 구현 전이라 "구현 상태"에서 구분해 둠.
> 숫자는 2026-11-23 기준.

## 한 줄 소개
고민과 기피 성분을 문장으로 말하면, 규칙 기반 추천 엔진이 근거와 함께 상위 3개 제품을 골라 주는 성분 기반 스킨케어 추천 서비스.

## 만든 이유
- 올리브영 근무 중 "홍조인데 뭐가 좋아요?" 같은 질문을 자주 받았지만, 사람마다 기준이 달라 짧은 시간에 판단하기 어려웠음.
- 기존 플랫폼은 판매·리뷰 중심이라 "잡티에 좋은 스킨, 근데 00 성분은 빼고" 같은 요구(고민 + 기피 성분)를 직접 들어주지 못함.

## 핵심 설계 결정 (면접에서 설명할 포인트)
1. **추천 판단은 규칙, LLM은 해석·설명만**
   - 추천 결과가 매번 달라지거나 근거 없이 나오지 않도록 점수·정렬은 규칙 엔진이 맡음.
   - LLM은 요청 해석(구조화 출력)과 설명 문장만 담당하고, 둘 다 검증을 거쳐 실패하면 템플릿으로 대체하는 구조로 설계함.
2. **게이트와 정렬을 분리 (점수 합산 안 함)**
   - 게이트: 민감성 자극 성분, 금지 성분, 사용자가 적은 기피 성분은 통과/탈락만 판정.
   - 정렬: 주력 고민 일치 수 → 핵심 성분 계열 수 → 함유 일치 수 → 선호 성분 순.
   - 이유: 합산 점수는 "왜 이 순위인지" 설명하기 어렵고, 기피 성분 같은 안전 조건이 점수에 묻힐 수 있음.
3. **전성분 표기 규칙 반영**
   - 함량 1% 초과 성분은 많은 순서로, 1% 이하는 순서 무관하게 적는 표기 규칙을 활용해 제품별 경계를 계산.
   - 알코올 같은 성분이 경계 뒤(소량)면 탈락시키지 않고 경고만 표시.
4. **사람이 검수한 정보만 사용**
   - 제품 100개(5개 카테고리 × 20개)를 직접 수집. 자동 크롤링은 약관·법적 문제로 하지 않음.
   - 성분 효능 태그는 출처(대한화장품협회 성분사전, 식약처 고시, EU CosIng, 논문)를 붙여 확인 가능한 것만 반영.
5. **성분 기반 판정의 한계를 데이터로 확인하고 방향을 바꿈**
   - 성분만으로 주력 고민을 정하면 브랜드가 내세우는 효능과 어긋나는 경우가 있었음 (예: 트러블 전용 세럼이 홍조로 분류).
   - 제품 100개를 제품명으로 검색해 브랜드가 말하는 효능을 6개 고민으로 분류하고 성분 초안과 비교: 완전 일치 34, 일부 겹침 43, 안 겹침 11, 성분 초안 없음 10 등으로 확인.
   - 결과: 주력 고민은 브랜드 효능(검색)을 기준으로 하고, 성분은 기피 성분 거르기와 근거 설명에 사용.

## 기술 스택
FastAPI, SQLAlchemy, MySQL(Docker), Alembic, React 19 + Vite, pytest.

## 이력서 한 줄 후보
- 성분 기반 스킨케어 추천 서비스 설계·개발: 고민·기피 성분 요청을 해석해 규칙 엔진으로 추천하고 근거를 제시하는 구조 (LLM은 해석·설명만 담당)
- 제품 100개 성분 데이터를 수기 수집·정제하고, 브랜드 효능과 성분 기반 판정의 불일치를 비교해 추천 기준을 재설계
- 게이트/정렬 분리 규칙 엔진과 단위 테스트 73개 작성

## 솔직한 한계 (질문받을 때 대비)
- 데이터가 100개로 적어, 고민 조합에 따라 일치 제품이 부족할 수 있음.
- 브랜드 효능은 판매처 설명·후기 기반이라 신뢰도가 낮은 항목 일부가 있음 (`search_concerns.csv`의 confidence 칸).
- 식물 추출물 다수는 성분 효능 출처가 약해 태깅하지 않음.
- 소량 성분 경계(1% 가정)는 표기 규칙에 근거한 추정이며 제품별 실제 함량은 알 수 없음.
- LLM이 쓰는 설명 문장과 해석 정확도 평가(20~30개)는 아직 없음. 현재 설명은 엔진 값으로 만든 템플릿이라 근거 밖 말이 나오지 않는 대신 표현이 단조로움.
- 카테고리별 주력 고민 분포가 치우쳐 있음(예: 토너 중 미백/톤·주름/탄력이 주력인 제품이 없음). 이 경우 챗봇이 다른 카테고리를 제안함.
